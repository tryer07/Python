# 文字冒险RPG实战（1）GM提示词：让AI当个守规则的主持人

> 这是系列的第一篇。我之前写过 FastAPI 猜字谜那个系列，八个接口怎么搭的都在那边讲过了，所以这个系列不再从跑通第一个接口讲起，直接聊这个项目里我新琢磨的东西。这个项目是个末世题材的文字冒险游戏：玩家在网页上输入自己干了什么，AI 主持人负责描写世界、判定战斗、记账血量。这一篇先解决最难的一件事：怎么让 AI 当一个守规则的主持人。

## 一、这次 AI 不是答题的，是当引擎的

猜字谜那局里，AI 只干一件事：出谜面、判对错。提示词写得不算讲究也能跑。

这个项目不一样，AI 要凭空撑一个世界。玩家输入"我去搜刮旁边的超市"，它得决定搜到什么、会不会碰上丧尸、掉不掉血，还要记住我三回合前埋过的伏笔。它从答题的变成了游戏引擎本身。我很快发现，提示词只要稍微含糊，它就开始糊弄我：战斗全是形容词，血量想掉多少掉多少，写着写着还爱加 Markdown 符号。所以我做的第一件事不是写接口，是坐下来给这个主持人写一份规矩。

## 二、人设和世界观放在最前面

我的系统提示词是这么开头的：

```
你是一名桌游主持人（GM），负责主持一场末世生存题材的文字冒险RPG。
玩家通过网页输入行动指令，你负责描写世界、扮演所有幸存者与威胁、
推进剧情、判定战斗与生存结果。

【当前玩家角色】
{character_block}

【主持规则】
1. 世界观：大灾变后的废土文明。城市沦为废墟，物资极度匮乏，
丧尸与变异生物四处游荡……剧情要连贯，你埋下的伏笔要记得回收。
```

这里有个我当时犹豫了很久的设计：`{character_block}` 是个占位符，不是写死的文字。玩家角色的名字、职业、血量、背包，每回合都会拼进这个位置。也就是下面第四节要讲的事，先按下不表。

## 三、把战斗规则写成数值锚点

这是我这篇里最想分享的一条经验。我一开始只写"你要判定战斗成败与伤害"，结果它十次有八次写成一刀秒杀的爽文，血量变化全凭心情。

后来我改成直接给它一张参照表：

```
3.1 战斗伤害参照（必须有明确数值变化，不许含糊带过）：
    - 玩家被普通丧尸抓伤：掉 5~12 HP；被精英或成群丧尸围攻：掉 15~25 HP；
      被变异体正面击中：掉 25~40 HP。
    - 逃跑、攀爬、翻窗等动作：成功则不掉血，失败掉 5~10 HP 或被围住。
    - 搜刮一处废墟：物资 +5~15；搜刮高风险区域可得更多，
      但必伴随一次遭遇判定。
```

给了区间之后，它的判定立刻像回事了：小丧尸挠人就掉几点血，硬拼变异体会重伤，因为表里写了上限。它还学会了在高风险搜刮后主动安排一次遭遇，因为我在条款里埋了"必伴随"三个字。

另外我加了一条自检条款，作用是防它当老好人：

```
3.2 状态数值只增不减是不允许的：每次行动后对照上文，
稍微盘点玩家还剩多少代价没付。
```

大模型天生爱顺着玩家，总想让他白拿好处。明确告诉我不许只涨不跌之后，捡东西掉血的平衡感出来了。

## 四、角色卡每次现拼，不指望它记忆

预设了三个职业，数值差别就是开局那一下的事，直接写死在字典里：

```
CHARACTER_CLASSES = {
    "退伍军人": {"hp": 110, "attack": 15, "gold": 30, "items": ["开山刀"]},
    "急救医生": {"hp": 90, "attack": 10, "gold": 40, "items": ["手术刀", "药品x2"]},
    "拾荒猎人": {"hp": 85, "attack": 13, "gold": 50, "items": ["自制弩", "匕首"]},
}
```

关键在第二节留的那个占位符。每次请求 AI 之前，我都会重新拼一段角色现状塞进去：

```
def build_character_block(session_data) -> str:
    character = session_data["character"]
    status = character["status"]
    return (
        f"姓名：{character['name']}（职业：{character['class']}）\n"
        f"当前状态：HP={status['hp']}/{status['max_hp']} 攻击={status['attack']} "
        f"物资={status['gold']} 背包={items_text}"
    )
```

我的思路是：数值账绝对不能交给 AI 的记忆去背。历史对话越长它记越不准，但系统提示词里这行状态是每回合现拼的，永远是最新事实，它想糊涂都难。真正的状态更新怎么同步回这个字典，靠的是回复末尾一行约定格式的状态标记，那是下一篇的正题。

## 五、调参和开局流程

请求用的还是那个 chat 接口，但两个参数我试了好几轮：

```
response = client.chat.completions.create(
    model="deepseek-chat",
    messages=messages,
    stream=False,
    temperature=0.85,
    max_tokens=800,
)
```

temperature 我试过 1.2（猜字谜那边的默认值），写剧情太飘，句子浮在天上不落地的感觉；调到 0.85 刚好，文字还有即兴感，但不会抒情泛滥。max_tokens 卡 800 是防它刹不住车，一次回复 150 到 300 字剧情加一行状态，800 个 token 富余够用，还逼着它学会说收。

开局接口 `POST /api/game/new` 的流程就四步：查职业名对不对，组装会话数据，让 GM 现写一段开场剧情，落盘存成 JSON。跟玩家后续回合比，它少了一步读历史而已。

## 六、状态那一行字里藏着什么

回看第二节的规则第 4 条，我要求 AI 每次回复的最末尾必须吐一行这样的东西：

```
[状态] HP=60/100 攻击=13 物资=25 背包=开山刀,绷带x2
```

剧情是写给人看的，这一行是写给程序看的。我用正则把它抠出来，同步进存档，再从展示文本里剔掉。这套小协议怎么设计、AI 不听话少吐了怎么办，就是第二篇《状态行协议：让 AI 把血量吐成程序能读的一行字》要讲的内容。
